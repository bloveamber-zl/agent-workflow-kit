# 可选测试用例驱动工作流设计

- 日期：2026-07-10
- 状态：已确认
- 适用项目：`agent-workflow-kit` 生成或升级的工作流

## 背景

当前工作流会按风险选择单元测试、Widget 测试、本地验收或 E2E/Patrol，但不会为每个需求固定生成独立测试用例。用户希望在明确提出“需要测试用例”时形成需求级测试用例，并支持两种场景：开发前先生成测试再实现功能，以及功能已经开发完成后根据原始需求补充测试并直接验证现有实现。

该能力必须保持可选。未明确触发时，项目继续使用现有默认验证配置，不生成测试用例文档，也不因需求风险主动提醒或自动启用。

## 目标

- 通过用户明确语义为单个需求启用测试用例驱动模式。
- 为启用模式的需求生成独立、可追踪的测试用例文档。
- 在业务实现前，为可自动化用例生成可执行测试并验证预期失败。
- 对已开发完成的需求生成测试用例和自动化测试，直接验证现有实现是否满足原始需求。
- 允许无法自动化的用例通过有原因、有步骤、有证据的人工验收完成。
- 保持现有默认工作流、状态模型和未启用项目的行为兼容。
- 将该主动能力同步登记到 `docs/workflow-capabilities.md`，便于后续查看和调用。

## 非目标

- 不为所有需求默认生成测试用例。
- 不因 L3/L4、高风险或核心链路自动提醒用户启用该模式。
- 不实现跨技术栈的 JSON/YAML 测试代码生成器。
- 不要求无法稳定自动化的真机、支付或第三方 App 场景伪装成自动化覆盖。
- 不新增全局任务状态。

## 触发规则

测试用例驱动模式只在用户对当前需求表达明确意图时启用，例如：

- “需要测试用例”
- “先生成测试用例”
- “走测试用例流程”
- “这是已经开发完成的需求，请根据需求生成测试用例并执行测试”
- 其他语义等价的明确表达

触发不要求位于消息末尾，也不依赖单一固定关键词。启用范围仅限当前需求，不修改项目长期默认配置。用户明确要求取消时，才允许退出当前需求的测试用例模式。

未出现明确触发语时：

- `test_case_mode` 为 `false` 或缺省。
- 不生成 `docs/test-cases/<requirement-id>.md`。
- 不提醒用户启用测试用例模式。
- 按项目已有 L0-L4、TDD、E2E、Patrol 和人工验收规则执行。

## 运行模式判定

启用测试用例流程后，Agent 根据用户描述和当前任务状态选择运行模式：

- `pre_implementation`：需求尚未实现，执行测试先行流程。
- `post_implementation`：需求已经实现，执行开发后验证流程。

用户明确说明需求已经开发完成时，优先选择 `post_implementation`。如果现有代码状态和用户描述冲突，应先检查当前任务、Git 历史和实现位置；仍无法判定时再向用户确认，不得擅自覆盖现有实现。

## 开发前工作流

启用后的流程为：

```text
需求解析
-> 测试用例设计
-> 开发文档与执行计划
-> 用户统一确认
-> 生成可执行测试
-> 验证测试按预期失败
-> 实现业务代码
-> 执行自动化测试
-> 执行必要的人工验收
-> 写回证据并完成需求
```

测试用例文档、开发文档和执行计划作为一个确认包提交给用户。测试用例未经确认、验收标准未映射到用例，或自动化与人工验收方式未说明时，不得进入业务编码。

## 开发后验证工作流

功能已经开发完成时，流程为：

```text
原始需求
-> 检查当前实现与相关历史
-> 生成测试用例
-> 用户确认测试用例
-> 生成自动化测试
-> 直接运行测试
-> 定位需求偏差、测试错误或环境问题
-> 修复或记录人工验收证据
-> 写回证据并完成验证
```

开发后模式必须以原始需求和验收标准为依据，不能根据当前实现反向修改测试目标。当前实现与已确认用例不一致时，应报告需求偏差并修复实现，不能削弱断言使测试迎合现状。

开发后模式不强制伪造“先红后绿”证据：

- 如果能够定位功能引入前的提交，可在隔离工作区或安全的历史版本上验证测试在旧实现失败。
- 如果无法恢复功能引入前状态，应记录“无修复前红灯证据”，并通过断言审查、负向场景和边界用例验证测试强度。
- 不得为了补红灯证据修改当前工作树或破坏用户未提交改动。

## 任务状态与字段

继续复用现有任务状态：

```text
designing -> planning -> approved -> implementing -> verifying -> done
```

`.agent/state/current-task.json` 按需增加：

```json
{
  "test_case_mode": true,
  "test_case_execution_mode": "pre_implementation",
  "test_case_doc": "docs/test-cases/REQ-XXX.md"
}
```

`test_case_execution_mode` 只允许 `pre_implementation` 或 `post_implementation`。未启用时字段允许缺省或设置为 `false`、空字符串，避免破坏已有工作流和目标项目。

## 测试用例文档

每个启用模式的需求生成：

```text
docs/test-cases/<requirement-id>.md
```

文档至少包含：

- 需求 ID、标题和确认状态。
- 用例 ID，例如 `TC-REQ-XXX-001`。
- 对应验收标准。
- 场景类型：正常、异常、边界或回归。
- 前置条件、操作步骤和预期结果。
- 验证方式：Unit、Widget、Golden、Patrol、其他 E2E 或人工。
- 自动化测试文件、测试名称或人工验收路径。
- 用例状态：待实现、预期失败、通过、人工通过或阻塞。
- 证据路径、不可自动化原因和剩余风险。

测试用例文档是当前需求测试设计的事实来源。开发文档、执行计划、追踪矩阵和测试报告引用用例 ID，不复制另一套可能漂移的完整用例内容。

## 自动化选择

Agent 根据项目技术栈、测试能力和用例性质选择最小可靠测试层级：

- 纯逻辑、解析、状态和边界条件：单元测试。
- 组件展示与交互：Widget、组件或浏览器组件测试。
- 稳定视觉输出：按项目能力使用 Golden 或截图比较。
- 页面链路、权限和原生交互：Patrol、Playwright 或项目既有 E2E 工具。
- 真机、真实支付、外部账号、第三方 App 或环境不可控链路：人工验收。

开发前模式的可自动化用例必须在业务实现前生成测试代码。开发后模式在测试用例确认后生成测试代码并直接运行。两种模式都必须完成测试用例自验证：

- 测试可以运行。
- 测试包含真实断言。
- 测试名称或注释可映射到用例 ID。
- 开发前模式中，功能未实现时测试因目标行为缺失而按预期失败。
- 开发后模式中，测试应能验证原始需求，而不是只证明当前实现可以运行。

无法可靠制造红灯时，必须记录原因，不得伪造失败证据。

## 人工验收降级

用例可以从自动化降级为人工验收，但必须同时满足：

- 记录无法自动化的具体原因。
- 保留可重复执行的前置条件和操作步骤。
- 记录验收环境、设备、账号类型或外部依赖。
- 保存截图、日志、视频、人工结论或其他有效证据。
- 说明剩余风险。

人工验收有完整证据时，该用例可标记为“人工通过”，不阻塞需求完成。

## 失败处理

测试失败按以下类型处理：

- 业务失败：修复实现并重新运行同一用例。
- 测试实现错误：修复测试代码，但不得削弱已确认的验收目标。
- 环境阻塞：记录设备、账号、后端、权限或工具问题，并按现有 blocker 规则处理。
- 不可自动化：满足人工降级条件后执行人工验收。

不得通过删除断言、跳过核心步骤或把失败测试改成只检查启动成功来获得通过结果。

## 追踪与完成条件

统一追踪链路为：

```text
需求 -> 验收标准 -> 测试用例 -> 自动化测试文件/人工步骤 -> 运行证据
```

启用测试用例模式的需求只有满足以下条件才能完成：

- 每个验收标准至少映射一个测试用例。
- 每个用例都有明确验证方式。
- 可自动化用例存在已运行的测试代码和结果。
- 人工用例存在降级原因、验收步骤和证据。
- 所有用例状态为“通过”或“人工通过”。
- active plan、追踪矩阵和测试报告中的状态一致。

## 兼容性

- 默认配置保持测试用例模式关闭。
- 现有 L0-L4、TDD、E2E/Patrol 和本地验收规则继续有效。
- 现有目标项目缺少新增字段或目录时仍可正常运行。
- 生成和升级脚本遵循现有非覆盖策略，除非用户显式使用 `--force` 或升级规则允许刷新 kit 管理文件。
- 简单样式需求只有在用户明确触发时才进入该流程；未触发时保持轻量验证。

## 主动功能说明页同步

`docs/workflow-capabilities.md` 是主动功能的统一查看和调用入口。本能力必须在该文档登记以下信息：

- 功能名：测试用例驱动验证。
- 状态：设计阶段为 `planned`，实现、验证和模板同步完成后改为 `enabled`。
- 对话触发方式：明确提出“需要测试用例”，或说明已开发完成并要求根据需求生成测试用例后执行测试。
- 默认目标：当前需求。
- 运行模式：开发前测试先行、开发后直接验证。
- 产出：`docs/test-cases/<requirement-id>.md`、自动化测试代码、测试报告和人工验收证据。
- 默认行为：未触发时不启用、不提醒，继续使用项目默认验证配置。

实施时必须同步更新：

- 当前仓库的 `docs/workflow-capabilities.md`。
- `scripts/generate_workflow.sh` 中的能力说明页初始化内容。
- `scripts/recon_project.py` 中的能力说明页重建内容，避免扫描回填覆盖该能力。
- 升级、校验和 self-test 链路，确保新生成及已升级项目均能看到该说明。

## 验收标准

- 未触发测试用例模式时，生成结果和现有默认行为一致。
- 明确提出“需要测试用例”时，工作流要求生成需求级测试用例文档。
- 明确说明需求已经开发完成时，工作流生成测试用例并直接验证现有实现，不要求伪造先红证据。
- 测试用例文档与开发文档、执行计划一起进入用户确认门禁。
- 开发前模式在业务实现前生成自动化测试；开发后模式在用例确认后生成测试并直接验证现有实现。
- 无法自动化的用例可通过完整人工证据完成。
- 追踪矩阵和测试报告能够按测试用例 ID 关联实现与证据。
- `docs/workflow-capabilities.md` 能说明两种运行模式、触发方式、默认关闭策略和产出位置。
- kit 自测覆盖默认关闭、显式启用、人工降级和兼容性场景。
